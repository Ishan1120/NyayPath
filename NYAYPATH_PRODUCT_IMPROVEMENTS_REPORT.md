## Detailed Product Improvement Breakdown

### 1. Legal Document Drafting

#### Problem Statement
Previously, the legal draft generated by the clarifying engine was transient, stored only in client React state without persistent database backing. It lacked structured demarcation between user-provided facts and AI legal formulations, did not highlight missing critical information, and risked silent overwrite on concurrent edits.

#### Technical Implementation
- **Database Schema:** Created migration `supabase/migrations/20261103000001_legal_drafts_schema.sql` defining `public.legal_drafts`:
  - `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
  - `user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE`
  - `case_id VARCHAR(100)`, `title VARCHAR(255)`, `document_type VARCHAR(100)`
  - `facts TEXT`, `legal_provisions TEXT`, `requested_relief TEXT`, `draft_content TEXT`, `lawyer_brief TEXT`
  - `status VARCHAR(50) DEFAULT 'DRAFT'`, `version INTEGER DEFAULT 1`
  - `created_at`, `updated_at` TIMESTAMPTZ
  - Row Level Security (RLS) enabled: `USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid())`
- **Backend Architecture (`api/legal_drafts.py`):**
  - Implemented `LegalDraftManager` providing full CRUD operations.
  - Implemented optimistic concurrency control: updates require `expected_version`; mismatch raises HTTP `409 Conflict`.
  - Built-in multi-tenant isolation: access is strictly authenticated; querying another user's draft raises HTTP `403 Forbidden`.
  - Fallback in-memory storage for offline development and test mock scenarios.
- **Draft Synthesis Enhancements (`api/clarifying_engine.py`):**
  - Refactored `synthesize_systematic_draft` to generate clearly delineated sections:
    1. `=== PART I: FACTUAL BASIS (USER-PROVIDED FACTS) ===`
    2. `=== PART II: LEGAL PROVISIONS & STATUTORY CITATIONS (AI-SUGGESTED) ===`
    3. `=== PART III: GROUNDS & PRAYER FOR RELIEF ===`
  - Automated missing-information warning banner (`=== ATTENTION / MISSING INFORMATION ===`) flagging missing incident dates, respondent authority names, or specific fee payment details.
- **Frontend Autosave & Versioning (`components/dashboard/DraftViewer.tsx`):**
  - Debounced autosave mechanism (1,500ms delay) updating the draft automatically as the user edits.
  - Interactive version badge displaying current persisted version and save status (`Saved`, `Saving...`, `Unsaved changes`).
  - "My Saved Drafts" drawer to list, load, and manage existing drafts.
  - Inline Markdown editor with real-time toggle between Preview and Edit modes.

### 2. Draft-to-Lawyer Connection

#### Problem Statement
Citizens had no direct mechanism to transmit an AI-generated draft or case brief to an advocate. Reaching a lawyer required re-entering grievance details manually, with no explicit sharing consent mechanism.

#### Technical Implementation
- **Backend Consultation Models (`api/lawyer_connect.py`):**
  - Updated `ConsultationCreateRequest` to accept `draft_id: Optional[str]` and `include_draft: bool = False`.
  - Stored attached draft metadata in `consultation_requests` table and memory cache.
  - Implemented duplicate pending request prevention: duplicate consultation requests for the same lawyer and case return HTTP `409 Conflict`.
- **Frontend Integration (`components/dashboard/DraftViewer.tsx`):**
  - Added primary "Connect with a Lawyer" action button directly in the draft viewer header.
  - Modal workflow with three key steps:
    1. **Lawyer Selection:** Queries verified advocates (`/api/lawyer/verified`) filtered by state, language, or specialization.
    2. **Draft Preview & Brief:** Allows adding a custom legal note/brief for the advocate.
    3. **Explicit Consent Checkbox:** Citizen must check `"I explicitly consent to sharing this legal draft and case summary with the selected advocate under advocate-client privilege."` before submitting.

### 3. Track SLA Page: Verified Deadlines vs. Unconfigured Categories

#### Problem Statement
The tracking page previously applied a universal 30-day countdown timer to all submitted cases, creating false urgency and legal inaccuracy for grievance types without a statutory 30-day mandate.

#### Technical Implementation
- **Watchdog Engine Rule Matrix (`api/watchdog_engine.py`):**
  - Introduced authoritative `STATUTORY_SLA_RULES` dictionary with statutory citations and enactment/verification dates:
    - **RTI:** Section 7(1), Right to Information Act, 2005 (30 days; 48 hours for life/liberty; verified: `2005-06-15`).
  - For categories without verified statutory SLAs (Civic Grievances, Campus Grievances, Consumer Inquiries):
    - `has_statutory_deadline = False`
    - `statutory_deadline_message = "No verified statutory deadline configured for this case."`
    - `response_due_date = None`, `first_appeal_due_date = None`, `days_remaining = None`, `is_overdue = False`
    - `section_20_penalty_inr = 0`
  - Replaced arbitrary countdown with precise progress metrics:
    - `time_elapsed_since_submission_seconds` and `time_elapsed_since_submission_formatted` (e.g. `12d 4h`)
    - `time_in_current_stage_seconds` and `time_in_current_stage_formatted`
    - `current_responsible_authority` and `next_expected_action`
- **Frontend Redesign (`app/track/page.tsx`):**
  - Replaced the countdown banner with conditional rendering:
    - If `has_statutory_deadline`: Displays statutory badge, authority, verified statutory citation, and countdown/penalty alert.
    - If non-statutory: Displays neutral status card with `"No verified statutory deadline configured for this case."`, alongside elapsed time since filing and duration in current inquiry stage.
  - Detailed milestone progress timeline displaying submission date, current stage, and expected next action.

### 4. Lawyer Workspace Complaint Timeline & Grounded AI Assistant

#### Problem Statement
Advocates reviewing shared cases had no unified chronological timeline of case events and lacked an intelligent case summary linked directly to verifiable evidence. Furthermore, access scope enforcement needed strict verification to ensure `METADATA_ONLY` grants do not expose full dossiers.

#### Technical Implementation
- **Aggregated Timeline Engine (`api/lawyer_connect.py`):**
  - Implemented `get_case_timeline_for_lawyer`:
    1. Verifies active `lawyer_case_access` record; non-active or absent access returns HTTP `403 Forbidden`.
    2. Enforces consent scope: `shared_scope` must be `FULL` or `CASE_AND_DOCS`. If `METADATA_ONLY`, immediately rejects with HTTP `403 Forbidden` (`detail="Consent scope is METADATA_ONLY..."`).
    3. Revocation is immediately effective: once revoked, all subsequent calls return HTTP `403 Forbidden`.
    4. Aggregates chronologically: initial submission, case activity logs, hearing schedules, meetings, and citizen lifecycle remarks.
    5. Strips confidential internal officer/proctor notes, raw passwords, tracking tokens, and PII vault data.
- **Grounded AI Case Intelligence Assistant (`api/lawyer_connect.py`):**
  - Implemented `generate_ai_case_summary`:
    - Clearly marked with `is_ai_generated: true` and formal legal disclaimer.
    - Structured output: `summary`, `key_developments`, `investigation_questions`, and `recommended_statutory_actions`.
    - Every key development is grounded and links to a specific `source_event_id` and `source_record` from the aggregated timeline.
- **Lawyer Case Dossier Page (`app/lawyer/cases/[id]/page.tsx`):**
  - Dedicated full-page case workspace featuring:
    - Case header with status, category, filing date, and verified consent scope badge (`CASE_AND_DOCS` / `FULL`).
    - Grounded AI Case Intelligence Assistant card with toggleable view and source references.
    - Chronological Interactive Timeline showing icons for submissions, proctor remarks, hearings, and meetings.
    - Attached documents drawer with signed download link triggers.

### 5. Tracking Key Experience & Authenticated Owner Separation

#### Problem Statement
Public case tracking via 128-bit verification key needed to ensure that no internal notes, proctor remarks, or personal identity documents leaked, while clearly providing a pathway for the true case owner to log in and access the full dossier.

#### Technical Implementation
- **Sanitized Public View (`api/citizen_workspace.py`):**
  - `track_case_public` returns rich, sanitized case progress:
    - Case ID, normalized category, status, and department.
    - Elapsed time since submission and duration in current stage.
    - Latest action taken and next expected step.
    - Strict exclusion: `proctor_notes`, `confidential_student_identities`, `tracking_key_hash`, and `verification_key_hash` are omitted.
  - Added security flags:
    - `requires_owner_auth_for_full_details = True`
    - `is_owner_authenticated = False` (or `True` if caller's session matches `user_id`).
- **Frontend Tracking Page (`app/track/page.tsx`):**
  - Added "View Full Complaint Details" action button on public tracking results.
  - Clicking launches modal prompting citizen to sign in or register to unlock full confidential dossier, encrypted documents, and direct officer messaging.
